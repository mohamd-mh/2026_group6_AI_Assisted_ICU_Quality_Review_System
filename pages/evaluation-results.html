Evaluation Procedure

Engineering Validation Approach

The evaluation combined data, model, workflow, and website/package checks. This is engineering validation for an academic prototype, not clinical validation and not evidence that the system is safe for live clinical deployment.

  • Data pipeline validation: checked that the processed MIMIC-III feature file loads correctly, expected fields are present, missing values are handled, and the application can consume the saved dataset, model metadata, and evaluation-result files.
  • Feature/target leakage check: verified that the supervised target label, hospital_expire_flag, is used for training/evaluation only and excluded from the model input features.
  • Model evaluation: evaluated the selected Logistic Regression model with accuracy, precision, recall, F1-score, ROC-AUC, and confusion matrix on the held-out test split.
  • Baseline comparison: compared the modular workflow output with a SIRS-style rule baseline using High-risk and At-risk detection framings.
  • Functional workflow testing: exercised the coordinator path from dashboard prioritization through Review Ticket creation, notes, checklist, Prepared Review Summary, status updates, and archive controls.
  • Website/package validation: checked the static project website pages, download links, user manual references, screenshots, and Software_System.zip package availability for final seminar submission.

The two result tables below come from two different evaluation procedures, described here before the numbers themselves.

Logistic Regression model

Held-out test split

The model was trained on a stratified 75/25 train/test split of patient_features_ai.csv (750 training rows, 250 held-out test rows, random_state=42). The Logistic Regression metrics table on this page is computed on the 250-row held-out test set only, which the model never saw during training.

Baseline vs. modular workflow

Full processed dataset

The SIRS-style baseline is a fixed rule, not a trained model, so the Baseline vs. Modular Workflow comparison table runs both pipelines across all 1000 rows of patient_features_ai.csv rather than the held-out split. This measures workflow behavior across the full processed cohort, not generalization to unseen data.

Target label

The supervised label is hospital_expire_flag (in-hospital mortality). It is used only to train and evaluate the model and is excluded from the model's input features.

Why multiple metrics instead of accuracy alone

The label is imbalanced: 894 survived vs. 106 died (10.6% mortality). A model that always predicted "survived" would already score about 89.4% accuracy while catching zero deaths, so accuracy alone would be misleading here. Precision, recall, F1, ROC-AUC, and the confusion matrix are reported together so both false negatives (missed deaths) and false positives (unnecessary review burden) are visible.

High-risk detection vs. At-risk detection

The mortality label is binary (survived/died), but both pipelines output three risk tiers (Low/Medium/High). To compare them against the binary label, each pipeline's output is scored two ways: High-risk detection counts only a "High" tier as a positive prediction, while At-risk detection counts "Medium" or "High" as positive. The two framings show how each pipeline performs under a stricter definition of risk versus a broader one.

Baseline vs Modular Workflow

Evaluation Results

Baseline uses the SIRS (Systemic Inflammatory Response Syndrome) criteria (Bone et al., 1992). SIRS-positive is defined as 2 or more of 4 criteria (temperature > 38C or < 36C; heart rate > 90/min; respiratory rate > 20/min; white blood cell count > 12,000/mm3 or < 4,000/mm3), mapped to Low (0-1 criteria), Medium (2 criteria, SIRS-positive), and High (3-4 criteria). Citation: Bone, R.C., Balk, R.A., Cerra, F.B., et al. (1992). "Definitions for sepsis and organ failure and guidelines for the use of innovative therapies in sepsis." Chest, 101(6), 1644-1655.

The modular workflow's improvement over the SIRS baseline is real but narrow. Of the 15 escalated cases (1.5% of 1000), 11 affect High-Risk detection (5 Low→High plus 6 Medium→High) and 9 affect At-Risk detection (5 Low→High plus 4 Low→Medium); the 6 Medium→High escalations don't change At-Risk classification since Medium already counts as at-risk. The escalated subset has a 40.0% true mortality rate vs. 10.6% overall (~3.8x enrichment), concentrated entirely in emergency admissions. With only 15 affected rows, the exact magnitude should not be treated as a stable, generalizable effect. The main workflow contribution remains transparency, traceability, documentation, and auditability rather than predictive accuracy.

Tradeoff

Precision and Recall

The dataset is imbalanced, with 106 positive labels out of 1000 rows. The default balanced Logistic Regression cutoff favors recall, which catches more positive cases but increases false positives. The tuned threshold raises precision and lowers recall. In a quality-review queue, this tradeoff affects workload: high recall can surface more cases for review, while higher precision can reduce unnecessary review burden.

Limitations

Known Limits

  • Metrics are based on the processed academic dataset and are not clinical validation.
  • Class imbalance makes precision/recall tradeoffs important.
  • Raw MIMIC files are not included, so preprocessing is documented but not reproduced from raw tables in the package.
  • The modular workflow improves transparency and documentation, but it is not an autonomous clinical decision-maker.
  • This is an academic prototype evaluation on a processed, held-out MIMIC-III feature table (patient_features_ai.csv, 1000 rows) - not a live clinical deployment. Regenerating the processed dataset or retraining the model may change these exact numbers.
